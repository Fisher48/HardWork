### Ускоряем код фреймворков в 100 раз

#### Дефолтная работа

**_Пример 1:_**  
В проекте интернет-магазина инструментов есть обычный метод, который выводит все категории и все подкатегории главной категории.
Суть в том, что при каждой очередной загрузке списка категорий они выводились в рандомном порядке. Вроде бы это никого не волновало, но заказчик изначально этого не указывал,
поэтому на этом акцент не делался. Хотя если рассудить по логике, лучше чтобы они были в одном порядке всегда и так красивее выглядит с точки зрения UI.
Я считаю, что это моё упущение и нужно смотреть всё наперед. Хоть я и делал список категорий в множестве `Set<Category>` т.к. хотел показать уникальность каждой категории, 
но не подумал о том, что у них не будет четкого порядка и можно было сделать либо `List<Category>` либо `LinkedHashSet<Category>`.

**_Пример 2:_**  
В проекте есть сервис парсинга Excel файлов и последующей записи обновленных цен всех товаров.
Иногда файл мог быть большим и возникала ошибка импорта Zip Bomb. Я не знал что это такое, пока не столкнулся с этим лично.
Получается xsl или xslx файлы имеют степень сжатия и если она слишком большая, то может срабатывать защитный механизм Zip Bomb Protection.
После указания в конфиге `ZipSecureFile.setMinInflateRatio(0.001)`, все сразу заработало. Моя ошибка т.к я не мог знать всё наверняка, но это полезно на будущее.
Я думаю с такими рода ошибками сталкиваются начинающие разработчики.

**_Пример 3:_**  
Работая с конфигом в ngix я выставил защиту от ботов и сканеров на уровне основного https, гду указывается ssl и т.д.
Но в логах обнаружил, что они все равно прорываются и оказалось что нужно еще указывать защиту на обычный http по 80 порту.

#### Нежелательные формы обработки

**_Пример 1:_**  
Как и говорил в примере ранее я заменил реализацию множества категорий на LinkedHashSet, сразу указывая на порядок категорий в множестве.

До:
```java
public class Category {
    // ... //
    private Set<Category> categories = new HashSet<>();
}
```

После:
```java
public class Category {
    // ... //
    private Set<Category> categories = new LinkedHashSet<>();
}
```

**_Пример 2:_**  
Статус заказ был как String, заменил его на Enum чтобы явно указать доступные статусы заказа. 
Так пользователь не сможет допустить ошибки при чтении или админ при выборе.

До:
```java
public class Order {
    ...
    private String status;
    ...
}
```

После
```java
 public class Order {
    // ... //
    private OrderStatus status;
    // ... //
}

public enum OrderStatus {
    CREATED, CONFIRMED, PAID, COMPLETED, CANCELLED
}
```

**_Пример 3:_**  
В глобальном обработчике ошибок указаны много различных типов ошибок, которые необходимо перехватывать.
Бывает что местами используется общие ошибки без указания конкретики, что может сбить с толку пользователя или разработчика при возникновении ошибки. 
Создал класс под конкретную ошибку для более удобной визуализации для пользователя или разработчика.
К примеру с изменением статуса обработки заказа.

До:
```java
@ExceptionHandler
public ResponseEntity<String> handle(Exception e) {
    return ResponseEntity.badRequest().body("Ошибка: " + e.getMessage());
}
```

После:
```java
public class OrderFinalizedException extends OrderStatusException {
    public OrderFinalizedException(String status) {
        super(String.format("Невозможно изменить статус заказа: заказ уже %s",
                getStatusDisplayName(status)));
    }
}

@ExceptionHandler(OrderFinalizedException.class)
public String handleOrderFinalized(OrderFinalizedException e,
                                   RedirectAttributes redirectAttributes,
                                   HttpServletRequest request) {
    log.warn("Попытка изменить завершенный заказ: {}", e.getMessage());
    redirectAttributes.addFlashAttribute("errorMessage", e.getMessage());
    return getRedirectUrl(request, "/admin/orders");
}
```


**Вывод:**  
В проектах бывают много различных библиотек, классов, фреймворков. Человек не может знать практически всё, хотя мы стараемся постичь много.
Иногда возникают подобные ситуации, что мы не учли контракт, спецификацию, пожелания заказчика или собственная гордость не позволила лишний раз залезть в доку.
В процессе работы всегда это разрешается путем неспешного анализа и тестирования, которе покажет верно ли мы считаем то, что должно быть действительным коде.
Ограничения необходимы как и спецификация она помогает как пользователям, так и разработчикам лучше разбираться в коде и не нагородить лишнего.
